# ADR-0017: v0.1 release assurance policy

- Status: Accepted
- Date: 2026-08-22
- Scope: Independent review, release assurance, and publication gates for
  `v0.1.0`

## Context

Earlier governance and security documents made an independent human security
and release review a mandatory gate before publishing `v0.1.0`. That assurance
is valuable, but making it a prerequisite for the first open-source release
could defer publication indefinitely without a practical security benefit
proportionate to the current local-first, read-only, single-user scope.

The release already has defense-in-depth evidence from CI, L05 testing, CodeQL,
Clippy, dependency and license checks, secret scanning, fuzzing, SBOM
generation, SHA-256 checksums, GitHub artifact attestations, native clean-install
tests, release-evidence review, and explicit owner authorization. These controls
reduce risk, but automated and AI-assisted checks are not an independent audit.

## Decision

An independent human security review is encouraged but is not required to
publish `v0.1.0`. It is a documented assurance target before `v1.0.0` and becomes
mandatory earlier if the project adds a materially higher-risk capability or
expands its trust boundary, including:

- network access or remote transport;
- privileged or executable extensions;
- source mutation;
- hosted or multi-tenant operation;
- durable memory;
- authentication; or
- another capability with comparable authority or exposure.

Publication of `v0.1.0` still requires every existing automated, internal,
provenance, packaging, GitHub release-environment, and owner-approval gate. The
release notes must disclose:

> This release has not undergone an independent third-party security audit.

They must also explain that the completed controls reduce risk but are not a
substitute for independent review. The project must not describe `v0.1.0` as
independently reviewed, audited, certified, or formally security assessed.

Package publication remains manual. The GitHub release environment and its
required owner approval remain separate publication controls.

## Rationale

This policy makes the current assurance level transparent while allowing an
early open-source release whose authority is deliberately narrow. Risk is
addressed through explicit residual-risk disclosure, automated and internal
security evidence, native release rehearsal, checksums and attestations, and a
human owner publication decision.

An independent review remains important as the product matures. A trust-boundary
expansion can make it mandatory before `v1.0.0`, rather than allowing the target
version to postpone review of newly introduced privileged behavior.

## Supersession boundary

This ADR supersedes only language that makes independent review a mandatory
`v0.1.0` release gate. It does not weaken or remove independent-review gates for
the separately governed Bridge Runner, privileged or executable extensions,
future higher-risk functionality, or human evaluation methodology.

## Consequences

### Positive

- `v0.1.0` can be published after its documented release gates and explicit
  owner approval pass.
- Users receive an exact disclosure of the release's assurance level.
- Higher-risk capabilities retain stronger review requirements.

### Costs and residual risk

- The first release will not have independent third-party security assurance.
- Automated and internal review can share blind spots with the implementation.
- The maintainer must reassess this decision whenever the trust boundary or
  privilege surface changes.

## Verification

- The prepared release notes contain the required security-review disclosure.
- Release evidence lists independent review as a deferred assurance target,
  not an open `v0.1.0` blocker.
- Repository policy review finds no conflicting mandatory independent-review
  gate for `v0.1.0`.
- Higher-risk independent-review requirements remain documented and unchanged.
